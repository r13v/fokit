# Production recipes

Use these recipes after the first generated form works. TanStack Form owns the
editable state. Keep requests, caches, persistence, and product workflows in
the application.

Use `form.api.Field` for an application-owned field, `form.api.FormGroup` for a
group path, and `form.api.Subscribe` for derived UI. Do not create a second form
binding for a custom panel on the same screen.

```tsx

```

The definition is fixed for that mount. TanStack Form can adopt changed
`defaultValues` while the form is untouched, but it protects touched work from
that replacement. Do not use prop identity as an edit-document workflow.
Remount for another document, or call `form.api.reset(nextInput)` after a
deliberate save or reload.

## Preserve the accessibility contract

Generated fields wire the structural slots to a control. A custom control must
attach the supplied name, ID, ref, and ARIA relationships to its interactive
element.

```tsx
// [!include ~/snippets/production-recipes.tsx:accessible-control]
```

Forward `blur`, honor `disabled`, `readOnly`, and `required`, and expose
`meta.invalid`. Custom slots must preserve semantic grouping, labels, issue
output, and usable buttons.

## Test the public experience

Test the form through public package imports and visible behavior:

1. Render the component that calls `kit.useForm`.
2. Find controls through labels and roles.
3. Enter schema input and submit through the visible button.
4. Assert issues, focus, transformed output, and pending UI.
5. Exercise application-owned request and resource branches separately.

Do not test private definition normalization or focus maps. Test a custom
control once against the `ControlProps` contract, then test product forms as a
user would operate them.

Read the [API reference](/api) for individual contracts and [Controls and
slots](/controls) for design-system integration.
