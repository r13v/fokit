# Build an async multiselect

An async multiselect is one field with clear ownership boundaries. TanStack
Form owns the selected IDs and form state. TanStack Query owns remote loading,
cancellation, and result caching. Floating UI coordinates popup positioning,
dismissal, focus, and list navigation. The control keeps only search text and
its option-label cache.

This separation keeps submission data small and stable. Labels can change or
be translated without making the form dirty.

## See it work

The trigger shows the first three selected cities as removable tags and
collapses the rest into a count. Open the list and search for `m`: matching
options remain selected in the list, and choosing another option does not close
the dropdown.

## Install the data and interaction layers

Install TanStack Form, TanStack Query, and Floating UI next to "Form, Please" and
your Standard Schema library:

```sh
npm install form-please @tanstack/react-form @tanstack/react-query @floating-ui/react zod
```

Create one `QueryClient` for the application and render
`QueryClientProvider` above forms that use the control. If the application
already uses TanStack Query, reuse its existing provider.

## Keep one field value

Model the selected values as one array field in the schema:

```tsx twoslash
import { z } from "zod"

const schema = z.object({
	cityIds: z.array(z.string()).min(1, "Choose at least one city"),
})
```

Use a `field` node with a custom control. Do not use an `array` UI node for
this widget: array nodes render repeatable rows with child fields, while the
multiselect edits one `string[]` value atomically.

## Delegate popup behavior

Use Floating UI's [`useFloating`](https://floating-ui.com/docs/usefloating) to
anchor the dropdown to the full trigger. Compose `useClick`, `useDismiss`,
`useRole`, and `useListNavigation` through `useInteractions`, then render the
open dropdown inside `FloatingFocusManager`.

This replaces manual document listeners, outside-click checks, focus-return
timers, viewport collision math, and the arrow/Home/End navigation switch. The
control still handles the product-specific action: toggling an ID without
closing the list.

Every value read by `queryFn` that changes the result belongs in `queryKey`.
TanStack Query then caches each search independently. Its query function also
receives an `AbortSignal`, which the real request should pass to `fetch`.

"Form, Please" UI resolvers remain synchronous. Pass `queryFn` inside the control's
`options` object; do not make the `options` resolver itself asynchronous.

## Preserve selected labels

The submitted value contains IDs, not `{ value, label }` objects. The control
keeps a small option cache so a selected tag remains readable when the next
search returns a different result set.

When an edit form starts with selected IDs, supply their labels through
`initialOptions`. A production application can load those records with the
form baseline or seed them from an existing TanStack Query cache.

## Submit the array value

The control receives one `string[]` value and updates it atomically with
`setValue`. TanStack Form keeps that array in its input state. The Standard
Schema validates the array during submit. "Form, Please" parses the successful
input a second time and passes the transformed output to `onSubmit`.

The visible trigger still receives `input.id`, `input.ref`, the described-by
relation, invalid state, and the disabled or read-only policy.

## Know the ownership boundary

- TanStack Form owns selected IDs, validation, touched state, and dirty state.
- "Form, Please" owns the definition, control contract, and generated structure.
- TanStack Query owns request status, cancellation, stale time, and cached
  search results.
- Floating UI owns positioning, dismissal, focus return, and list navigation.
- The control owns search text, selected-label caching, tags, and ID toggling.
- The server still validates that submitted IDs exist and are allowed.
