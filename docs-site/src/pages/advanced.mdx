# Production recipes

Reach for these patterns after the generated form path is working. They keep
the same schema, definition, and form instance while letting product-specific
UI own more of the experience.

## Compose generated and bespoke UI

Use `kit.Fields` for the ordinary generated part, then render previews,
summaries, or commands against the same `FormInstance`.

```tsx twoslash
// @jsx: react-jsx
import {
	createFormKit,
	nativeControls,
	useForm,
	useFormState,
} from "form-please"
import { z } from "zod"

const schema = z.object({ name: z.string() })
const kit = createFormKit({ controls: nativeControls })
const definition = kit.defineForm(schema)({
	ui: [
		{
			kind: "field",
			path: "name",
			control: "text",
			label: "Name",
		},
	],
})

// ---cut---
function ProfileEditor() {
	const form = useForm(definition, {
		defaultValues: { name: "" },
	})
	const dirty = useFormState(form, (snapshot) => snapshot.isDirty)
	let status = "Saved"
	if (dirty) status = "Unsaved changes"

	return (
		<kit.Form form={form}>
			<kit.Fields />
			<output>{status}</output>
			<kit.Submit>Save profile</kit.Submit>
		</kit.Form>
	)
}
```

`useValue`, `useField`, `useArrayField`, and `useFormState` subscribe only to
the selected slice. Keep generated and manual controls inside the same
`kit.Form` so they share submission, reset, and accessible error behavior.

## Load an edit-form baseline

`defaultValues` is read when the form instance is created. Changing the prop
does not overwrite edits. When loaded server data should become the new clean
baseline, reset deliberately:

```tsx twoslash
// @jsx: react-jsx
import { createFormKit, nativeControls, useForm } from "form-please"
import { useEffect } from "react"
import { z } from "zod"

const schema = z.object({ name: z.string() })
const kit = createFormKit({ controls: nativeControls })
const definition = kit.defineForm(schema)({
	ui: [
		{
			kind: "field",
			path: "name",
			control: "text",
			label: "Name",
		},
	],
})

// ---cut---
function ProfileEditor({
	profile,
}: {
	readonly profile: { readonly name: string }
}) {
	const form = useForm(definition, {
		defaultValues: profile,
	})

	useEffect(() => {
		form.reset(profile)
	}, [form, profile])

	return (
		<kit.Form form={form}>
			<kit.Fields />
		</kit.Form>
	)
}
```

In a real edit screen, avoid replacing `profile` with a new object on every
render. A successful `reset(profile)` clears touched state, issues, submission
metadata, and dirty state.

When switching between distinct create/edit records should discard the current
instance completely, key the component at that product boundary instead:

```text
<ProfileEditor key={profile.id} profile={profile} />
```

Use a stable mount after loading for one baseline, `reset(profile)` for an
explicit in-place baseline replacement, and `key` when identity itself changes.
`AutoForm` never resets merely because a new `defaultValues` object was created.

## Treat FormData as untrusted

`parseFormData` rejects prototype keys, structural collisions, sparse arrays,
unknown reserved metadata, excessive depth, and oversized indexes before
schema validation.

Request size, multipart parsing, file count, and file size limits still belong
in the framework before parsing. Server schemas should coerce browser protocol
values such as number and date strings into domain values.

See the complete server round trip in
[React 19 Actions](/guides/react-19-actions).

## Preserve the accessibility contract

Form, Please supplies stable IDs, native names, described-by relationships, issue
focus targets, required state, and form semantics. Controls and slots decide
the final markup, so they must forward the props they receive.

- Controls attach `input.id`, `input.name`, `input.ref`, and
  `input["aria-describedby"]` to the successful native control.
- Field slots connect `labelProps` and `descriptionProps`.
- Error slots render `rootProps` so submit-time focus reaches the correct
  issue.
- Disabled, read-only, and required states remain semantic, not only visual.

## Test the public experience

Test forms through the DOM your user receives:

- find controls by label and submit through the native form;
- assert visible issues and focus recovery after invalid submit;
- move array rows and verify their values stay with the logical row;
- test custom controls and slots through the markup they own;
- test server flows with serializable `FormResult` values.

Use `form-please/core` for focused store invariants. Application tests should not
depend on private store fields or generated DOM order.
