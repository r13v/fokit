## One explicit model

A form built with Form, Please has three parts: a schema for validity, a UI
definition for structure, and a kit for rendering.

```tsx twoslash
// @jsx: react-jsx
import { createFormKit, nativeControls, type FormInput } from "form-please"
import { z } from "zod"

const profileSchema = z.object({
	name: z.string().min(1, "Name is required"),
	email: z.string().email("Enter a valid email"),
	newsletter: z.boolean(),
})

const kit = createFormKit({ controls: nativeControls })

const profileDefinition = kit.defineForm(profileSchema)({
	ui: [
		{ kind: "field", path: "name", control: "text", label: "Name" },
		{
			kind: "field",
			path: "email",
			control: "text",
			label: "Email",
			options: { type: "email" },
		},
		{
			kind: "field",
			path: "newsletter",
			control: "checkbox",
			label: "Send me product news",
		},
	],
})

const defaultValues = {
	name: "Ada Lovelace",
	email: "ada@example.com",
	newsletter: true,
} satisfies FormInput<typeof profileSchema>

export function ProfileForm() {
	const form = kit.useCreateForm(profileDefinition, { defaultValues })

	return (
		<kit.AutoForm
			form={form}
			onSubmit={({ value }) => console.log(value)}
		>
			<kit.Submit>Save profile</kit.Submit>
		</kit.AutoForm>
	)
}
```

### Schema owns validity

Form, Please accepts any Standard Schema implementation. Your schema is the source of
truth for validation. It also defines editable input and validated output.

### UI definition owns structure

Define fields, sections, arrays, conditions, and layout explicitly.
Form, Please does not guess a product UI from schema metadata. A schema change cannot
silently change the interface.

### Your kit owns rendering

Start with `nativeControls`. Replace controls and structural slots with your
design-system components when needed. The form definition and state model stay
the same.

## The responsibility boundary

| Form, Please owns | Your application owns |
| --- | --- |
| Typed form state and granular subscriptions | The schema library and domain rules |
| Validation, issues, focus, and submit lifecycle | Field choice, labels, and product workflow |
| Stable arrays and dynamic UI resolution | Controls, slots, styling, and layout |
| Native names and FormData coordination | Server persistence and business effects |

Use the same definition with `kit.AutoForm`. You can also compose it manually
with `kit.Form`, `kit.Fields`, and granular hooks.

Create each form through its exact kit. Bind an existing form with
`kit.useBindForm`. A base kit, an extended kit, and two sibling kits have distinct
owners, even when their controls have the same structure.

## When to reach for Form, Please

Use Form, Please when a form needs schema validation, typed transformations,
conditional fields, stable arrays, generated and manual rendering, or client
and server submission under one state model.

For a small form with uncontrolled inputs and one submit handler, native HTML
is usually the smaller tool.
