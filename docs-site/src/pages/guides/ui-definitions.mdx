# Design the form UI

The schema decides whether data is valid. The `ui` tree decides what a person
sees, how fields are grouped, and which control edits each value. Keeping those
decisions separate lets a domain schema evolve without silently redesigning the
form.

`kit.defineForm(schema)({ ui })` validates the tree once, freezes it, and keeps
the result reusable across form instances.

## Read the tree at a glance

Every node has one of four jobs:

| Node | Owns | Children |
| --- | --- | --- |
| `field` | One typed value path, its control, copy, and interaction state | none |
| `section` | A semantic group and an optional one-to-four-column layout | other UI nodes |
| `array` | One repeatable value path and the editor for each item | relative UI nodes |
| `render` | Form-local React content with no field contract | none |

A section can contain fields, nested sections, arrays, and render nodes. An
array repeats fields, sections, and nested arrays for every item, resolving
their paths relative to that item.

## Connect paths to controls

A field joins the data model to the rendering kit:

| Property | Purpose |
| --- | --- |
| `path` | A canonical typed path such as `"name"` or `"address.city"` |
| `control` | A key from the kit's control registry |
| `options` | Options inferred from the selected control |
| `label`, `description` | Accessible product copy rendered by the field slot |
| `required` | Required presentation, native state, and ARIA |
| `valuePolicy` | What happens to an optional value when the field becomes hidden |

TypeScript rejects unknown paths, incompatible controls, and options that do not
belong to the selected control. For example, a number path accepts the shipped
`number` control but not `date`.

`required` does not add a validation rule. Generated forms use the Standard
Schema as the source of truth, so required validation belongs in the schema.

## Compose structural copy

In React kits, field labels and descriptions, section titles and descriptions,
and array labels and descriptions accept `string | ReactElement`. Use this for
inline links, emphasis, badges, or a tooltip trigger that remains part of the
node's accessible structure:

```tsx twoslash
// @jsx: react-jsx
import {
	createFormKit,
	nativeControls,
	type FieldSlotProps,
} from "fokit"
import { z } from "zod"

type ProductFieldOptions = {
	readonly labelTooltip?: string
}

function ProductTooltip({
	id,
	content,
}: {
	readonly id: string
	readonly content: string
}) {
	return (
		<span className="product-tooltip">
			<button aria-describedby={id} type="button">
				<span aria-hidden="true">?</span>
				<span className="sr-only">About this field</span>
			</button>
			<span id={id} role="tooltip">
				{content}
			</span>
		</span>
	)
}

function ProductField({
	rootProps,
	label,
	labelProps,
	description,
	descriptionProps,
	slotOptions,
	control,
	errors,
}: FieldSlotProps<ProductFieldOptions>) {
	const tooltipId = `${labelProps.htmlFor}-tooltip`

	return (
		<div {...rootProps}>
			<label {...labelProps}>{label}</label>
			{slotOptions?.labelTooltip === undefined ? null : (
				<ProductTooltip
					content={slotOptions.labelTooltip}
					id={tooltipId}
				/>
			)}
			<div {...descriptionProps}>{description}</div>
			{control}
			{errors}
		</div>
	)
}

const schema = z.object({ name: z.string() })
const kit = createFormKit({
	controls: nativeControls,
	slots: { Field: ProductField },
})

// ---cut---
kit.defineForm(schema)({
	ui: [
		{
			kind: "field",
			path: "name",
			control: "text",
			label: <strong>Display name</strong>,
			description: <a href="/naming-policy">Read the naming policy</a>,
			slotOptions: {
				labelTooltip: "This is visible to other members",
			},
		},
	],
})
```

`slotOptions` belongs to structural presentation; field `options` still belongs
to the selected value control. `Field`, `Section`, and `Array` each infer an
independent options type from the slot registered in `createFormKit`. The
property is also resolvable, so tooltip copy or other presentation data can
depend on tracked values and runtime context.

The React-free `fokit/core` default remains string-only. React elements and
slot-option objects are opaque to core normalization: their internals are not
cloned or frozen. Treat them as immutable after defining the form; mutating an
opaque object does not notify the form store or trigger a render.

The tooltip example keeps its interactive trigger outside the field label and
connects it to `role="tooltip"` content. Product CSS or a design-system tooltip
can reveal that content on hover and keyboard focus.

## Place form-local React content

Use a render node when a preview, command, or other React component belongs at
an exact position but does not represent one field:

```tsx twoslash
// @jsx: react-jsx
import {
	createFormKit,
	nativeControls,
	useFormContext,
	useFormState,
} from "fokit"
import { z } from "zod"

const schema = z.object({ name: z.string() })
const kit = createFormKit({ controls: nativeControls })

function NamePreview() {
	const form = useFormContext<typeof schema>()
	const name = useFormState(form, (snapshot) => snapshot.values.name)
	return <output>{name}</output>
}

// ---cut---
const definition = kit.defineForm(schema)({
	ui: [
		{
			kind: "render",
			id: "name-preview",
			component: NamePreview,
		},
	],
})
```

Fokit owns only the render node's ID, order, and mounting. The component
receives no props; hooks provide form state. Its contents get no automatic
path, copy, errors, layout, inherited interaction state, accessibility, or
FormData behavior. Render nodes are allowed at the root and inside sections,
but not inside array rows.

`ActionForm` still renders them and ignores them during compatibility checks.
Any successful form controls inside the component are application-owned.
Because the definition embeds a component reference, it is React-only and
cannot cross a serializable React Server Components boundary.

## Group fields and describe layout

A section has a required `id`, optional `title` and `description`, and a
`children` array. Set `columns` to `1`, `2`, `3`, or `4`; the default is `1`.

Direct children can set `span` to a column count or `"full"`. Inside a section,
fields default to one column while nested sections and arrays default to the
full row. Import `fokit/layout.css` for the shipped responsive grid, or forward
the same layout props through a custom `Section` slot.

`className` is static escape-hatch metadata for product styling. It does not
change the form state model.

## Derive UI from tracked values

Properties described as resolvable accept either a value or a resolver function.
Fokit tracks the paths read by the resolver and invalidates its cached result
only when one of those values changes. The resolver can also read runtime
`context` without adding that data to form values.

| Node | Resolvable properties |
| --- | --- |
| `field` | `label`, `description`, `slotOptions`, `required`, `visible`, `disabled`, `readOnly`, `options` |
| `section` | `title`, `description`, `slotOptions`, `visible`, `disabled`, `readOnly` |
| `array` | `label`, `description`, `slotOptions`, `visible`, `disabled`, `readOnly` |

Structure stays static: paths, controls, children, layout, classes, and array
defaults are not resolvable. Change resolvable properties for dynamic UI;
compose manually when the product needs a different tree.

Resolvers are synchronous and pure. Fetch remote options in application data
flow, pass them through `context`, and let a resolver select the relevant result.

See [Conditional fields](/guides/conditional-fields) for tracked-value and context
examples.

## Let interaction state flow through the tree

Visibility and interaction state inherit from their parents:

```text
visible  = parent visible  AND node visible
disabled = form disabled   OR parent disabled OR node disabled
readOnly = form readOnly   OR parent readOnly OR node readOnly
```

Hiding a section hides its complete subtree. Disabling or making a section
read-only also affects every descendant; arrays apply those states to add,
remove, and reorder actions. `required` is field-only and does not inherit.

### Choose disabled or read-only

Use the state that describes what the person can do, not just how the control
should look:

| State | Use it when | What the person experiences |
| --- | --- | --- |
| `disabled` | The control or form is currently unavailable | Controls cannot be edited or focused. Form-wide `disabled` stops submission before submit-time validation. |
| `readOnly` | The value should remain available but must not change | Controls stay enabled, named, and focusable, while all mutation paths are guarded. The form can still be submitted. |

For example, disable a form while its workflow is unavailable; make it
read-only for a review or confirmation step. If both states resolve to `true`,
disabled behavior takes precedence.

`disabled` and `readOnly` retain values in the form store and validated output.
They are interaction policies, not data-removal policies.

## Choose what hidden means for data

Visibility and stored values are separate decisions:

| `valuePolicy` | Result when a field becomes hidden |
| --- | --- |
| `"preserve"` | Keep the value so it returns when the field is shown again. This is the default. |
| `"unset"` | Remove the value through the normal transaction pipeline. |

`"unset"` is available only for paths that can be absent or contain
`undefined`. That keeps a UI transition from violating the editable input type.

Hidden values still follow schema validation. If visibility changes whether a
value is required, express that rule in the schema as well as in the UI.

## Repeat relative fields with arrays

An array node names an array `path`, provides `itemDefault`, and describes one
item with relative child paths:

| Property | Purpose |
| --- | --- |
| `path` | A typed path whose value is an array |
| `itemDefault` | A complete new item or a function that creates one |
| `children` | Fields, sections, or nested arrays relative to the item |
| `label`, `description` | Copy for the complete repeatable group |

Object defaults are cloned for every append, so rows do not share mutable
containers. Stable row keys remain internal UI metadata and never enter form
values or submitted data.

Read [Arrays](/guides/arrays) for commands, row identity, array errors, and
native `FormData`.

## Know the generated boundary

Generated definitions deliberately keep a narrow contract:

- each data path appears once within its scope;
- explicit node IDs are unique;
- fields and arrays derive an ID from their path, while sections and render
  nodes require one;
- standalone arbitrary content is explicit through a React-only render node.

Use `AutoForm` children for workflow content after generated nodes. When
product layout needs exact placement beyond a render node, compose `kit.Form`,
`kit.Fields`, and granular hooks around the same definition and form instance.
Always take `Form` and `Fields` from the same kit. React context cannot encode
that runtime pairing, so TypeScript cannot detect components mixed from
different kits.

renderers, [Styling](/guides/styling) to apply the structural grid, or
[Production recipes](/advanced) for manual composition.
