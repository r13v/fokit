# Async fields

Form, Please owns typed form values; an application data layer owns remote options.
Keep that seam explicit and async fields stay cancellable, cacheable, and
testable without giving the form store a second network lifecycle.

## Choose the integration shape

Use a custom control when the async picker is a reusable editor for one value.
Use a render node when the search UI is local to one form or writes several
related schema paths. Both shapes keep the selected IDs in Form, Please and request
state outside it.

The complete reusable-control version is the
[async multiselect guide](/guides/async-multiselect). The render-node shape is
useful for registry lookup, title suggestions, address resolution, and similar
product workflows.

## Keep requests in the data layer

TanStack Query passes an `AbortSignal` to the request and caches results by the
search key. The render component subscribes only to the form values it needs:

```tsx twoslash
// @jsx: react-jsx
import { useQuery } from "@tanstack/react-query"
import {
	type RenderNodeProps,
	useFormContext,
	useValue,
} from "form-please"
import { useState } from "react"
import { z } from "zod"

type Organization = { readonly id: string; readonly name: string }
const applicationSchema = z.object({ organizationId: z.string().optional() })
declare function searchOrganizations(
	search: string,
	signal: AbortSignal,
): Promise<readonly Organization[]>

function OrganizationSearch({ disabled, readOnly }: RenderNodeProps) {
	const form = useFormContext<typeof applicationSchema>()
	const selectedId = useValue(form, "organizationId")
	const [search, setSearch] = useState("")
	const results = useQuery({
		queryKey: ["organizations", search],
		queryFn: ({ signal }) => searchOrganizations(search, signal),
		enabled: search.trim().length >= 2,
	})

	return (
		<section aria-busy={results.isFetching}>
			<input
				disabled={disabled}
				onChange={(event) => setSearch(event.currentTarget.value)}
				readOnly={readOnly}
				value={search}
			/>
			{results.data?.map((organization) => (
				<button
					aria-pressed={organization.id === selectedId}
					disabled={disabled || readOnly}
					key={organization.id}
					onClick={() => form.setValue("organizationId", organization.id)}
					type="button"
				>
					{organization.name}
				</button>
			))}
		</section>
	)
}
```

Debounce the search string before it enters the query key when the endpoint
needs it. Do not use the Form, Please schema-validation debounce as a request debounce;
the two lifecycles answer different questions.

## Project resource state into fields and sections

When loaded data affects ordinary definition properties, put its current state
in form context and map all three outcomes with `fromResource`. The selector
and active case stay synchronous, so ordinary resolver dependency tracking
still applies:

```ts twoslash
import {
	createFormKit,
	fromResource,
	nativeControls,
	type NativeSelectOption,
	type ResourceState,
} from "form-please"
import { z } from "zod"

const schema = z.object({ city: z.string() })
const kit = createFormKit({ controls: nativeControls })

type Context = {
	readonly cities: ResourceState<readonly NativeSelectOption[], Error>
}

kit.defineForm(schema).withContext<Context>({
	ui: [
		{
			kind: "section",
			id: "location",
			disabled: fromResource(
				(_values, { context }) => context.cities,
				{
					pending: () => true,
					success: () => false,
					error: () => true,
				},
			),
			children: [
				{
					kind: "field",
					path: "city",
					control: "select",
					options: fromResource(
						(_values, { context }) => context.cities,
						{
							pending: () => ({ options: [] }),
							success: ({ value }) => ({ options: value }),
							error: () => ({ options: [] }),
						},
					),
				},
			],
		},
	],
})
```

Use the same helper for `visible`, `readOnly`, labels, descriptions, control
options, and typed `slotOptions`. It does not fetch anything and does not accept
an async selector. In particular, `ui: [fieldPromise]` is not supported:
definition topology, paths, controls, metadata, and serialization remain known
synchronously.

## Choose a pending presentation

Map the resource at the narrowest boundary whose layout should change:

| Desired experience | Mapping |
| --- | --- |
| Keep layout stable | Section or field `disabled: true` while pending |
| Avoid showing an irrelevant field | Field or section `visible: false` while pending |
| Preserve the expected shape | Show a sibling render-node skeleton while pending and the field while successful |
| Block the entire form | Derive `useForm` or `kit.AutoForm` `disabled` with `matchResource` |

For a skeleton, use complementary exhaustive resolvers instead of an implicit
loading flag:

```ts twoslash
import { fromResource, type ResourceState } from "form-please"

declare const cities: ResourceState<readonly string[], Error>

const showSkeleton = fromResource(
	() => cities,
	{
		pending: () => true,
		success: () => false,
		error: () => false,
	},
)
const showField = fromResource(
	() => cities,
	{
		pending: () => false,
		success: () => true,
		error: () => false,
	},
)
```

If a temporarily hidden field uses `valuePolicy: "unset"`, hiding it can clear
its value. Prefer `disabled`, a skeleton, or the default `"preserve"` policy
when loading must not discard an existing edit value.

For the complete form, match before rendering:

```text
const disabled = matchResource(permission, {
  pending: () => true,
  success: ({ value }) => !value.canEdit,
  error: () => true,
})

return <kit.AutoForm definition={definition} disabled={disabled} {...props} />
```

`matchResource` can also choose between a page skeleton, an error state, and
the form itself when the definition or its initial values must not render yet.
That choice belongs to application composition rather than an async UI node.


The adapter uses TanStack Query's `isRefetchError` discriminant to preserve

successful value. `QueryResourceState` structurally satisfies what
`fromResource` needs while retaining query-specific `fetchStatus` and `refresh`
details in narrowed cases.

## Preserve selected labels

The form should normally store a stable ID, not a whole remote record. Seed the
query cache from the loaded record, keep an `initialOptions` list, or load the
selected ID with a separate query so its label survives a search-result change.

This matters in edit forms: a selected value must remain understandable before
the user types a new search. It also prevents a temporary empty result from
silently clearing a valid form value.

## Surface loading and errors deliberately

Loading, empty results, retry, and request failures belong to the async
component. Submission failures that invalidate a form path belong on the form:

```ts twoslash
import type { FormInstance } from "form-please"
import { z } from "zod"

const schema = z.object({ organizationId: z.string().optional() })
declare const form: FormInstance<typeof schema>

// ---cut---
form.setErrors([
	{
		source: "server",
		path: "organizationId",
		message: "That organization is no longer available",
	},
])
```

The server issue clears when that path changes. A transient suggestion request
failure should usually stay local to the picker so it does not make the whole
schema invalid.

## Keep the ownership boundary

| Concern | Owner |
| --- | --- |
| Selected typed ID or IDs | Form, Please values |
| Schema validity and submitted output | Standard Schema |
| Search text, open state, keyboard navigation | Control or render component |
| Request cache, cancellation, retries | Application data layer |
| Current availability projection | `matchResource` or `fromResource` |
| Selected-label hydration | Query cache or loaded record |
| Rejected submission issue | Form, Please server error |

Form, Please intentionally has no query-library dependency or remote-options API. The
local `queryToResource` helper above is an integration recipe, not package
state. See [studio policies](/examples/studio-policies) for resource-backed
resolvable properties, or the [research grant](/examples/research-grant) and
[learning cohort](/examples/learning-cohort) examples for render-node
variations. You can also return to [Production recipes](/advanced).
