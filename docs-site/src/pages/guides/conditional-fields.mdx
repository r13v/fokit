# Conditional fields

Conditional form UI should be predictable: a resolver reads the values it
needs, Form, Please recomputes only when those values change, and value retention stays
an explicit product decision.

## Derive UI with resolver functions

Use a function anywhere a UI node accepts a resolvable value, including
`visible`, `disabled`, `readOnly`, `required`, labels, descriptions, and control
options.

```ts twoslash
import { createFormKit, nativeControls } from "form-please"
import { z } from "zod"

const schema = z.object({
	accountType: z.enum(["personal", "company"]),
	companyName: z.string().optional(),
})
const kit = createFormKit({ controls: nativeControls })

const definition = kit.defineForm(schema)({
	ui: [
		{
			kind: "field",
			path: "accountType",
			control: "select",
			label: "Account type",
			options: {
				options: [
					{ value: "personal", label: "Personal" },
					{ value: "company", label: "Company" },
				],
			},
		},
		{
			kind: "field",
			path: "companyName",
			control: "text",
			label: "Company name",
			visible: ({ accountType }) => accountType === "company",
			valuePolicy: "unset",
		},
	],
})
```

Form, Please tracks every canonical path read during the synchronous resolver call.
The cached result is reused until one of those values or the runtime `context`
reference changes. If a resolver takes a different branch next time, its
tracked paths change with that branch.

Because `defineForm` binds the schema first, TypeScript contextually types each
resolver, autocompletes destructured paths, and infers every value. Nested
canonical paths use an alias such as
`({ "address.country": country })`. Invalid paths and incompatible return
values fail type checking; imports and explicit type arguments are not needed.

Read paths explicitly through the resolver's first argument. Rest
destructuring, spread, and enumeration with `Object.keys()` are rejected because
they would hide which values affect the result. Resolvers stay synchronous and
pure; remote loading belongs in application data flow, not inside a resolver.

A function assigned directly to a resolvable property is always a resolver. If
a custom control option contains callbacks, keep them inside an options object:
`options: { filter: (item) => item.active }`.

## Decide what happens to hidden values

Visibility and stored data are separate:

| Policy | Behavior |
| --- | --- |
| `"preserve"` | Keep the current value when a node becomes hidden. This is the default. |
| `"unset"` | Remove the value through the normal transaction pipeline. |

Use `"preserve"` for temporarily hidden preferences that should return when the
user reopens a section. Use `"unset"` when a hidden value must no longer be
submitted or validated.

`"unset"` is available only for optional paths. That type constraint prevents a
conditional UI change from making the editable input structurally incomplete.

## Pass loaded data through context

Context is runtime-only data. It can drive options and interaction state but
never becomes form data and never makes the form dirty.

```tsx twoslash
// @jsx: react-jsx
import { createFormKit, nativeControls } from "form-please"
import { z } from "zod"

const schema = z.object({ country: z.string() })
type ProfileContext = {
	readonly countries: readonly {
		readonly value: string
		readonly label: string
	}[]
	readonly locked: boolean
}

const kit = createFormKit({ controls: nativeControls })

const definition = kit
	.defineForm(schema)
	.withContext<ProfileContext>({
		ui: [
		{
			kind: "field",
			path: "country",
			control: "select",
			label: "Country",
				readOnly: (_values, { context }) => context.locked,
				options: (_values, { context }) => ({
					options: context.countries,
				}),
			},
		],
	})

function ProfileForm({ countries, locked }: ProfileContext) {
	return (
		<kit.AutoForm
			definition={definition}
			defaultValues={{ country: "" }}
			context={{ countries, locked }}
		/>
	)
}
```

Load countries before rendering the form, then pass them through `context`.
Replacing context recomputes resolved UI without replacing the form instance.

## Keep conditional validation in the schema

`visible` controls rendering; it does not rewrite validation rules. Use schema
refinements for cross-field requirements:

```ts twoslash
import { z } from "zod"

const schema = z
	.object({
		accountType: z.enum(["personal", "company"]),
		companyName: z.string().optional(),
	})
	.superRefine((value, context) => {
		if (
			value.accountType === "company" &&
			(value.companyName ?? "").trim() === ""
		) {
			context.addIssue({
				code: "custom",
				path: ["companyName"],
				message: "Company name is required",
			})
		}
	})
```

This keeps the same rule in classic submit, imperative validation, and server
parsing.
