# Build a production form

This tutorial builds a focused production variant of the form from
[Get started](/get-started). It explains:

- validation that starts after blur and updates after a change;
- a company field that appears only when relevant;
- repeatable contacts with stable row identity;
- transformed, typed output at submit.

The completed editor starts with valid profile data. It shows field issues after
blur, removes an irrelevant company value, and reports the contact count after
submit.

## Before you start

Complete [Get started](/get-started) first. This tutorial uses the same React
and TypeScript application with `form-please` and Zod installed.

The tutorial uses two adjacent files:

- `form-kit.tsx` contains the schema, kit, definition, and default values.
- `basic-form.tsx` contains the React component.

The finished form uses the shipped native controls. You can connect your design
system later without changing the schema or form state.

## Verify the completed form

Complete these checks in order:

1. Clear the name and blur it. The field shows its schema issue.
2. Choose Company. The company field appears.
3. Switch back to Personal. `companyName` leaves the stored input.
4. Add, reorder, or remove a contact. Its row state stays attached correctly.
5. Submit. The callback receives transformed output with `contactCount`.

The editable input does not contain `contactCount`. The validated output

callbacks.

The schema also contains the cross-field company rule. The same rule works in
client validation and server parsing. You do not need to duplicate it in a
component.

## Describe the product UI

The definition maps typed schema paths to controls. It makes two product
decisions explicit:

- `companyName` depends on `accountType` and is removed when hidden;
- `contacts` supplies a complete new-row value and relative child fields.

The schema-bound resolver function infers each value that it reads. Form, Please tracks
those paths and reuses the result until a tracked value changes. The function
is synchronous and pure.

`valuePolicy: "unset"` removes `companyName` when the field becomes hidden. This
policy is valid because `companyName` is optional in editable input.

The array node does not add hidden IDs to your values. Form, Please keeps stable row
keys as UI metadata while paths, touched state, and visible issues move with
the logical row.

## Know what is already handled

This form now has:

- complete typed defaults and deterministic reset;
- native labels, names, FormData, and submit semantics;
- submit-time focus for the first visible invalid field;
- blur-first validation and change revalidation;
- stable array commands and accessible default action labels;
- a clear boundary for custom controls and structural slots.

Successful submission does not reset the form. After you persist the value,
choose the baseline that your product needs:

```ts twoslash
import type { FormInstance } from "form-please"
import { z } from "zod"

const schema = z.object({ name: z.string() })
declare const form: FormInstance<typeof schema>
declare const saved: { readonly name: string }

// ---cut---
form.reset(saved)
```

`reset(saved)` replaces both current values and the dirty-comparison baseline,
which is the usual edit-form behavior after a successful save.

## Fix common implementation problems

### The company field does not clear

Set `valuePolicy: "unset"` on the field. Keep `companyName` optional in
`FormInput`, because Form, Please must be able to remove it.

### A new contact starts with missing properties

Make `itemDefault` a complete contact input. Form, Please uses this value when the user
adds a row.

### A contact loses its touched state after reordering

Use the array commands exposed by Form, Please. Do not reorder only the values
in application code. Form, Please keeps row identity and field state together.

### Submit produces no output

Correct the visible schema issues and submit again. `onSubmit` runs only after
successful validation.
