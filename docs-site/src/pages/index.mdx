# Forms that stay typed, native, and yours

Fokit turns an explicit form definition into a production-ready React form. It
handles state, validation, dynamic UI, arrays, accessible error relationships,
and native submission while your application keeps its controls, markup, and
visual language.

Use it when handwritten field wiring has become the risky part of a form, but
handing the UI to a theme or schema-to-form generator would be an even bigger
compromise.

## One explicit model

The shortest path has three parts: a schema that owns validity, a UI definition
that owns structure, and a kit that maps control names to renderers.

```tsx twoslash
// @jsx: react-jsx
import { createFormKit, nativeControls, type FormInput } from "fokit"
import { z } from "zod"

const profileSchema = z.object({
	name: z.string().min(1, "Name is required"),
	email: z.string().email("Enter a valid email"),
	newsletter: z.boolean(),
})

const kit = createFormKit({ controls: nativeControls })

const profileDefinition = kit.defineForm(profileSchema)({
	ui: [
		{ kind: "field", path: "name", control: "text", label: "Name" },
		{
			kind: "field",
			path: "email",
			control: "text",
			label: "Email",
			options: { type: "email" },
		},
		{
			kind: "field",
			path: "newsletter",
			control: "checkbox",
			label: "Send me product news",
		},
	],
})

const defaultValues = {
	name: "Ada Lovelace",
	email: "ada@example.com",
	newsletter: true,
} satisfies FormInput<typeof profileSchema>

export function ProfileForm() {
	return (
		<kit.AutoForm
			definition={profileDefinition}
			defaultValues={defaultValues}
			onSubmit={({ value }) => console.log(value)}
		>
			<kit.Submit>Save profile</kit.Submit>
		</kit.AutoForm>
	)
}
```

### Schema owns validity

Fokit accepts any Standard Schema implementation. The schema is the single
source of truth for validation and for the difference between editable input
and submitted output.

### UI definition owns structure

Fields, sections, arrays, conditions, and layout stay explicit. Fokit does not
guess a product UI from validation metadata, so changing a schema never silently
changes what a user sees.

### Your kit owns rendering

Start with `nativeControls`, then replace controls and structural slots with
your design-system components. The form definition and state model do not have
to change when the renderer does.

## The responsibility boundary

| Fokit owns | Your application owns |
| --- | --- |
| Typed form state and granular subscriptions | The schema library and domain rules |
| Validation, issues, focus, and submit lifecycle | Field choice, labels, and product workflow |
| Stable arrays and dynamic UI resolution | Controls, slots, styling, and layout |
| Native names and FormData coordination | Server persistence and business effects |

This boundary lets the same definition render through `kit.AutoForm` or be
composed manually with `kit.Form`, `kit.Fields`, and granular hooks.

## When to reach for Fokit

Fokit is a fit when a product needs schema-owned validation, typed
transformations, dynamic fields, stable arrays, generated and manual rendering,
or client and server submission under one state model.

If the form is a handful of uncontrolled inputs and a submit handler, native
HTML may already be the smaller and better tool.
