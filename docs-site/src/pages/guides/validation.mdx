# Validation and errors

Fokit keeps three concerns separate: your schema decides what is valid, the
form instance decides when validation runs, and the interaction that triggered
validation decides which errors are visible.

That separation lets a form stay quiet on first render, explain a failed submit
clearly, and remove stale server errors as soon as the user corrects a field.

## Start with the default

The default behavior fits most forms:

| Option | Default | Effect |
| --- | --- | --- |
| `mode` | `"submit"` | Do not validate untouched input until submit. |
| `revalidateMode` | `"change"` | Revalidate an invalid form while the user fixes it. |
| `asyncDebounceMs` | `0` | Run change-triggered async validation without a delay. |

You do not need to configure validation to get a useful submit flow.
`kit.AutoForm` validates the complete Standard Schema, skips `onSubmit` when
invalid, exposes the errors, and focuses the first visible editable field that
needs attention.

Use blur-first validation when early feedback helps:

```tsx twoslash
// @jsx: react-jsx
import { createFormKit, nativeControls } from "fokit"
import { z } from "zod"

const schema = z.object({
	email: z.string().email("Enter a valid email"),
})
const kit = createFormKit({ controls: nativeControls })
const definition = kit.defineForm({
	schema,
	ui: [
		{
			kind: "field",
			path: "email",
			control: "text",
			label: "Email",
			options: { type: "email" },
		},
	],
})

// ---cut---
const form = (
	<kit.AutoForm
		definition={definition}
		defaultValues={{ email: "" }}
		validation={{
			mode: "blur",
			revalidateMode: "change",
			asyncDebounceMs: 250,
		}}
	>
		<kit.Submit>Continue</kit.Submit>
	</kit.AutoForm>
)
```

`asyncDebounceMs` applies only to async validation scheduled by a change.
Blur, imperative validation, and submit always run immediately. Newer
validation wins over stale async results.

## Understand error visibility

Fokit may know about an issue before it shows that issue. This keeps raw schema
state separate from the feedback a person should see.

- Blur exposes issues owned by the blurred path.
- Change exposes overlapping issues when change validation runs.
- `validate(path)` exposes issues for that path and its descendants.
- `validate()` and submit expose the complete form result.
- `setErrors` immediately exposes the supplied server or manual issues.

Controls receive `meta.displayErrors` and `meta.invalid`. Default slots render
the same visible issue list and connect it through `aria-describedby`.
Invisible fields cannot render a local error, so an exposed issue falls back to
the form error summary.

## Install server errors

Classic client submission can install a rejected server result on the same
form instance:

```ts twoslash
import type { FormInstance } from "fokit"
import { z } from "zod"

const schema = z.object({ email: z.string().email() })
declare const form: FormInstance<typeof schema>

// ---cut---
form.setErrors([
	{
		source: "server",
		path: "email",
		code: "already_registered",
		message: "This email already has an account",
	},
])
```

A server issue becomes stale when the user edits its path. A form-level server
issue becomes stale after any value change.

Use `source: "manual"` for durable application feedback that should remain
until `form.clearErrors()` or reset:

```ts twoslash
import type { FormInstance } from "fokit"
import { z } from "zod"

const schema = z.object({ email: z.string().email() })
declare const form: FormInstance<typeof schema>

// ---cut---
form.setErrors([
	{
		source: "manual",
		message: "Saving is paused while the account is locked",
	},
])

form.clearErrors()
form.clearErrors("email")
```

Schema issues are owned by schema validation. Imperative APIs cannot forge or
selectively clear them.

## Validate deliberately

`validate()` returns transformed schema output on success. `validate(path)`
still evaluates the complete schema so cross-field refinements stay correct,
but returns only issues for the requested subtree.

```ts twoslash
import type { FormInstance } from "fokit"
import { z } from "zod"

const schema = z.object({
	age: z.string().transform(Number),
	email: z.string().email(),
})
declare const form: FormInstance<typeof schema>

// ---cut---
const emailIssues = await form.validate("email")
const result = await form.validate()

if (result.success) {
	result.value.age.toFixed(0)
}
```

Imperative validation does not mark fields touched and does not increment the
submit count.

## Choose the right ownership boundary

Use classic `onSubmit` when the browser form should validate before a client
callback. Use [React 19 Actions](/guides/react-19-actions) when the server Action
owns parsing and validation. Both paths use the same schema issues and field
paths, but they intentionally have different submission lifecycles.
